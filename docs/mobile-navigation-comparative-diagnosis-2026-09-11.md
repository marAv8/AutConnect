**Gesture, readiness, mount and state details**

ClientCarousel attaches `useGuardedSwipe` to its stage, disables it while an overlay is active, blocks interactive/menu targets, and reserves browser edges. It changes Client index, not route history depth; its owner callback replaces the active orbit URL. Field Observation applies the guarded hook to its internal cards with a 24px edge exclusion. Case Support’s inspected workspace, Provider and request carousels use chevron-controlled local card state; they do not install an application route-Back swipe. Clinical forms have their own local section controls; the carousel’s route-level swipe is disabled beneath their overlay. None of this proves what a physical Safari edge gesture paints. See [guarded hook](../components/useGuardedSwipe.ts#L96), [carousel configuration](../app/dashboard/ClientCarousel.tsx#L282), and [Case Support cards](../app/portal/case-support/[clientId]/CaseSupportWorkspaceCarousel.tsx#L10).

The menu is a body portal. A normal launch waits for its existing exit `animationend`; reduced motion completes synchronously. The closing layer is inert; the final handler flushes dismissal before invoking route/overlay opening. Its local state resets on Client-key remount. A menu image in a Safari transition alone cannot distinguish a mounted menu, compositor preview, or outgoing layer. Current tests found no mounted menu during observed returns; they cannot rule out unsampled paint or browser preview.

The orbit slide has `initial={false}` and animates only drag offset. ClientOrbit reads the stage’s content-box dimensions in a layout effect and observes resizing; it does not deliberately hide the stage while measuring. Its provider reveal effect runs on Client/presentation-key change or remount. The return marker validates owner/root/Client/provider arrangement before choosing settled presentation. That mechanism currently accepts Supervisor history only and is prepared by Field Observation (and explicitly by the synthetic settled-return fixture), not Case Support. See [slide](../app/dashboard/ClientCarouselSlide.tsx#L17), [reveal/measurement](../app/dashboard/ClientOrbit.tsx#L380), [marker](../app/dashboard/dashboardOrbitRestoration.ts#L1).

Focused overlays notify their Dashboard owner in a layout effect; the shell removes utilities and their reserved padding. A ResizeObserver can therefore run around workflow changes even though the orbit stays mounted. This is a justified workspace-layout difference, not evidence of the phone flash. The carousel marks readiness in DOM and emits a separate 650ms Team Focus event; that event is not proof of hydration, stable paint, or a navigation blocker. See [focused state and readiness](../app/dashboard/ClientCarousel.tsx#L115), [workspace padding](../app/globals.css#L643).

There are demonstrated overlapping state responsibilities: owner React mode/Client state, owner history metadata, Next’s URL/search-param snapshot, and carousel local Client index. Owners both restore in an initialization effect, a popstate handler, and a search-param-dependent effect; carousel separately consumes overlay history. These serve different transitions but require consistent ordering. ClientCarousel computes `initialIndex` only for initial state, then reports its local index back to its owner. Do not add another restoration cache on top of these owners.

**Confirmed causes versus unresolved hypotheses**

1. **Confirmed cause of reproduced Case Support entrance replay:** route remount runs ClientOrbit’s reveal effect; `openCaseSupport` does not attach a presentation marker and the marker reader is Supervisor-specific. Provider Case Support returns replayed all three entrances on both browser and synthetic visible Back, first and repeat, in both projects. Field Observation’s exact marker produced zero reveal-ready nodes. This is a presentation finding with correct destinations, not a diagnosis of the intermittent phone flash.
2. **Confirmed cause of reproduced overlay Forward gap:** `prepareOverlayHistory` stores only `autConnectDashboardOverlay: true`; workflow/provider/kind remain local React state. Back clears that state. Forward has neither a descriptor to restore nor an active-ref branch to reopen it. Both new Forward cases reached the marked history entry without a workflow. This is independent of the unreproduced wrong Back destination.
3. **Confirmed source difference in Case Support visible Back:** it pushes a Client-orbit URL rather than consuming W. This explains why later browser Back can revisit Case Support on that route sequence. It does not explain browser Back from W landing on grid, and the actual visible control was not exercised here.
4. **Wrong destination and reported brief flash:** no confirmed cause; no evidence yet establishes whether they share one. Correct-return entrance replay demonstrates that presentation changes can occur without a destination error. It does not prove the phone symptoms are independent.

**Smallest proposed repair — not implemented**

For the **reproduced Case Support native-return entrance replay only**, reuse the existing presentation marker: allow it to validate the appropriate Supervisor or Provider history owner, and attach the exact current Client/root/provider-arrangement marker by replacing O immediately before the existing Case Support route push, after menu closure. Keep the marker on that existing entry. Do not push a recovery entry, create a second cache, or use a global animation flag. Leave same-page overlay presentation alone.

This would address the observed remount entrance because the current reveal effect already settles a matching presentation. It must be gated by matching owner, orbit URL, authorized Client, root and arrangement. Preserve Field Observation’s token transfer and trusted Back, real Client-change remounts, direct/reload fallback behavior, menu closure, Team-sharing, draft behavior, Case Support authorization and all data semantics. Shared-helper regression risk is accidentally settling a different Client/provider arrangement or trusting the wrong role’s entry. It does not resolve Case Support’s real visible-Link history sequence; that is a separate proposed change requiring a validated route-origin design and real-control tests before implementation.

For **wrong-to-grid Back and the phone flash**, no production repair is justified yet. Capture one failure with the branch evidence above; then change the responsible existing owner only. If initialization overwrites a validated live orbit, correct that resolver before any replacement. If listener lifecycle is implicated, move subscription lifecycle outside the one-time initialization guard. Neither is asserted as the phone fix now. Overlay Forward, if required, needs a validated minimal workflow descriptor in its existing X entry and a symmetric restore branch; defer it from a Back-only patch rather than inventing extra entries.

**Separate Delete finding — requirement only, no implementation**

Required behavior: deleting a Clinical Note must soft-delete the whole note and all its revisions from everyone’s ordinary application views, retaining underlying records for authorized audit/retention.

Current [Delete UI](../app/portal/notes/add/EntrySpecializedForms.tsx#L199) appears in edit mode. [Its handler](../app/portal/notes/add/EntryForm.tsx#L1070) confirms “This cannot be undone,” sends `clientId` and `kind` to `deleteSupervisorEntry`, then refreshes/closes on success. It sends no selected entry ID or revision ID. [The server action](../app/actions/deleteSupervisorEntry.ts#L8) requires a session and Supervisor role, accepts ClinicalNote or SupervisorObservation, and finds **the current author’s entry for server-local today** by the compound unique key. It has no separate active Client-assignment check. It physically deletes that Entry and revalidates Dashboard. Missing entry/invalid data/forbidden are returned; missing session throws.

This is not a revision-only action or a general historical whole-note soft-delete action. The [schema](../prisma/schema.prisma#L533) has no Entry tombstone. EntryRevision, AssessmentItem, AbcObservation and EntryRead relations cascade when Entry is deleted, so revisions and related records are removed rather than retained. Do not run it as part of diagnosis.

A separate implementation would need stable note identity, explicit author/role/current-Client authorization and an audited deletion operation; a parent tombstone with actor/time can hide all revisions through the parent while retaining every row. Ensure ordinary revision access cannot bypass that parent filter; audit access must be separately authorized. Update both [API history](../app/api/notes/history/route.ts#L51) and [standalone history](../app/portal/notes/view/page.tsx#L59), form-data/edit loaders, Dashboard current/recent entry queries, direct note/revision access, derived signals and AI/context queries. History GET currently creates/updates EntryRead rows, so filter deleted parents **before** acknowledgement. Filter completion/unread derivation through active parents while retaining audit read records; do not republish or acknowledge a deleted note. Relevant starting points: [Dashboard entries](../app/dashboard/page.tsx#L92), [Client signal inputs](../app/libs/clientSignal/server.ts#L28), [read lifecycle](../app/libs/entryReadState.ts#L1).

Also define create/update behavior against today’s unique provider/Client/date/kind key: a tombstone must not be silently resurrected by an existing upsert, nor block intended new-note behavior without an explicit policy. Cover all revisions, authors and shared/private readers with synthetic tests. Deletion must not change unrelated Case Support notifications or team-focus unread state.

Stopping point: diagnosis and repair proposal only. Added the comparative test, this report and sanitized evidence; no production navigation or deletion changes.
